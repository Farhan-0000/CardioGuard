# Implementation and Results

This chapter describes how the design of Chapter 3 was implemented and what the measurements show. It first walks through the implementation layer by layer and presents the user interface. It then reports the testing strategy and the evaluations of individual components: retrieval, model selection, PII redaction, the emergency classifier, performance and the knowledge-base corpus, followed by the adversarial code review that preceded the final experiments. The results of the hallucination study and of the live system benchmarks follow, and the chapter closes with the limitations of the work. Every number in this chapter is read from a results or measurement file in the repository; values that do not exist yet are marked as pending.

## Implementation Details

MedBridge is implemented in Python 3.11 as one FastAPI application with an asynchronous request path, a plain JavaScript web client and a separate evaluation package. The code is organised by layer, as shown below; unit and integration tests sit beside the application code, and cross-layer tests in the top-level `tests/` directory.

### Application, Configuration and API

The application lifespan (`medbridge/main.py`) opens the database pool, starts the model warm-up and the retention job as background tasks and mounts the web interface. Warm-up loads the encoders and the reranker, probes Qdrant and asks Ollama to load the gate and generator models with a keep-alive period, so the first patient message does not pay the model-loading cost that dominated the Review-3 latencies; readiness is reported by `/health`, and if warm-up fails the application still serves requests and loads models lazily. All settings live in one `Settings` class (`medbridge/config.py`) whose defaults run fully locally: Ollama only, local-only mode, gate temperature 0.0, generator temperature 0.3, seed 42, loop-breaker at 2, speculative retrieval, redaction, encryption and authentication enabled. Per-role settings allow a smaller model for the extractor and gates, V1 and V2 are off by default, and secrets are generated by `scripts/setup_env.py` and never committed.

The API (Appendix E) returns, for every message, the response text, action, citations, loop-breaker counter, redaction count and full `Explanation`. The streaming endpoint runs the same orchestrator call in a background task with its own database session and bridges the progress callback to Server-Sent Events: `stage` events while the pipeline runs, then `meta`, `token` events that replay the validated text, and a final `done` with the complete response (or `error` followed by a safe `done`). A client that disconnects does not stop the turn, which still completes and is persisted, and a request for an erased session is answered with HTTP 410 before any pipeline work.

### Pipeline Orchestrator and AI Layer

The orchestrator replaces the original 540-line method with one short method per stage over the shared `TurnContext` (Section 3.2). Its collaborators (classifier, extractor, projector, gates, retriever, reranker, generator, turn store, redactor, verifier) are injected through the constructor, so unit tests can replace any of them with a fake and check every route, fallback and invariant without a running model. Production always calls `process_message` with the full configuration; the evaluation harness passes an ablation preset.

All language-model calls go through `ResilientLLMWrapper`. For Ollama it uses the native chat endpoint with *structured outputs*: the JSON schema of the expected Pydantic model is sent as the `format` parameter, so decoding is grammar-constrained and small local models return complete, valid JSON. Each call sets temperature, seed, context size, a token limit and nucleus sampling (1.0 for deterministic calls, 0.95 for the generator), with "thinking" disabled on hybrid reasoning models and a shared HTTP client with explicit timeouts. Failed attempts are retried with exponential backoff; a reply truncated by the token limit counts as a failure, is retried once with a doubled budget and is never repaired or cached; when every attempt fails the wrapper returns `None` and the orchestrator applies the specification fallback. A per-turn call log records role, model, latency, tokens, attempts, truncation and cache status for the trace and the evaluation.

Every prompt has a system part (role, inputs, ordered decision rules and a few examples on topics absent from the benchmark) and a user part containing only data blocks: `<patient_context>`, `<conversation_history>`, `<clinical_evidence>` and `<untrusted_user_input>`. The extractor sees the last four turns so it can resolve references such as "that dose", and its output is post-processed deterministically (generic drug names with brand and class kept, BP events reconciled with the BP parser, search query expanded). The generator has the production `grounded` mode and the evaluation-only `direct`, `vanilla` and `prompt_safety` modes used by C0 to C2.

### Retrieval, Ingestion and Persistence

The embedding client encodes a query with both models concurrently and caches the result; the retriever sends one Qdrant query with dense and sparse prefetch branches (20 candidates each) and RRF with *k* = 60, caches non-empty results for a configurable time, and raises an explicit `RetrievalError` on infrastructure failure so that an outage is never mistaken for "nothing relevant found". The reranker holds one cross-encoder per process, runs it in a worker thread under a lock and selects CUDA, Apple MPS or the CPU automatically. Ingestion (`python -m medbridge.ingestion`) is the only writer to Qdrant: it verifies each file against the manifest checksum, parses and cleans PDF and HTML documents, extracts tables, chunks text by tokens and stores each chunk with document, organisation, year, section, page range, URL, topics, checksum and content type; unchanged documents are skipped and `--stats` writes the corpus statistics used in this report.

The turn store is the single writer of a turn. It encrypts every text field with the session cipher, splits the trace into an identifier-free public part and an encrypted private part, locks and re-projects the snapshot, writes all rows and flushes once. Four Alembic migrations define the schema: the initial schema with the append-only rules, an enumeration fix, the privacy migration (session keys, feedback, trace and erasure columns) and a uniqueness constraint on feedback. The privacy package (Section 3.6) is used by these layers: redaction returns the redacted text with counts per category, the crypto module caches unwrapped keys and invalidates them on erasure, FastAPI dependencies enforce tokens on every protected route, and the retention job reuses the erasure code path.

### Complementary Features

Three features were added around the pipeline without bypassing the gates.

- **BP log and trends.** `GET /api/sessions/{id}/context` returns the decrypted snapshot and the BP series from the event log, each reading classified into the ACC/AHA categories (normal, elevated, stage 1, stage 2, severe range of 180/120 mmHg or above) by a deterministic function (`medbridge/features/bp.py`). `POST /api/sessions/{id}/bp` checks a manually entered reading for plausibility and stores it as a BP_READING event through the same projection, so the chart and the gates see the same data; a severe reading returns fixed advice to re-measure and call the emergency number if symptomatic, without replacing the fast-path.
- **Clinician summary export.** `GET /api/sessions/{id}/summary` produces a Markdown or JSON summary (`medbridge/features/summary.py`) with the patient-reported snapshot, the categorised BP log and each question and answer with its action and citations, under a disclaimer that it is not a diagnosis or a medical record.
- **Administrator dashboard.** `/dashboard`, behind the administrator login, shows the action distribution, gate decisions, fallback and loop-breaker counts, per-stage latency percentiles, feedback, redaction statistics and recent audit entries in redacted form, from `GET /api/metrics` and `GET /api/admin/audit`.

Feedback (thumbs up or down with an optional comment) is stored once per assistant message, with the comment redacted and encrypted.

### Evaluation Package and Harnesses

The evaluation package (`evaluation/`) implements Section 3.7: dataset schema and seeded split, a runner that sends every item through the production orchestrator under each preset and writes one record per turn with the full explanation and evidence, degraded-turn classification, memoisation, both judges, calibration, statistics, analysis with tables, figures and an error report, the human annotation sheet, retrieval evaluation and model selection. Runs are resumable item by item, accept `--limit` for dry runs and stop with a circuit breaker after consecutive degraded items. The MedBridge-AQ, RABBITS and adversarial harnesses and the smoke, load and latency scripts now run live against the real pipeline; their mock modes remain only as harness self-tests, clearly labelled as routing simulators.

## User Interface

The Streamlit interface of Review 3 relied on styling workarounds and lacked the interaction patterns of a modern chat assistant. It was replaced by a single-page application served by FastAPI (`medbridge/web/`), written in plain HTML, CSS and JavaScript modules with no build step, external fonts or third-party scripts, so that it runs offline and satisfies the strict Content Security Policy. Markdown is rendered by a small escape-first renderer that escapes all text before adding the few elements it controls. The figures in this section show the main screens; the others are in Appendix B.

[[table:reranker_ablation]]

All intervals overlap, and no reranker was significantly better than the default or than fusion alone. Two factors probably contribute. The query set is small, and the relevance labels are page-level matches found by regular expressions, so a reranker that promotes a relevant passage from a page or document that was not labelled is not rewarded; the labels may therefore under-credit reranking. The default `ms-marco-MiniLM-L-6-v2` reranker was nevertheless kept, for three reasons: the reranking stage is part of the specified architecture; it is the fastest of the candidates; and its score is used as the quantitative evidence-sufficiency signal of the calibrated Evidence Gate (V1) and as the ranking variable of the risk-coverage analysis, roles that fusion scores, being rank-based, cannot play. The evaluation does show that a medical reranker such as MedCPT is a reasonable candidate for future work, but no change is justified by the present data.

## Model Selection

### Method

The application model performs four tasks: extraction, both gate decisions and generation. It must fit in the 6 GB of GPU memory of the target laptop at 4-bit quantisation. Three open-weight candidates available in the Ollama library were compared: `gemma3:4b` (the Review-3 model), `qwen3.5:4b` and `qwen3:8b` [@gemmateam2025gemma3; @yang2025qwen3]. For each candidate, the model-selection script (`evaluation/model_selection.py`) runs condition C5 on the HalluBench development split, never the test split, and records strict and lenient routing accuracy with Wilson intervals, per-class precision and recall, macro-F1, the share of calls per role whose JSON output was valid on the first attempt, per-turn latency (median and 95th percentile) and effective generation throughput. Routing accuracy here compares the pipeline's action with the gold action; it measures the gates, not hallucination.

### Round 1 (Before the Final Prompt Revision)

A first round was run on {{model_selection_r1.generated_at|date}} with the prompts as they stood before the adversarial code review and the routing-rule revision; its results are kept as `evaluation/results/model_selection_round1_prefix/` and shown below.

[[table:model_selection_round1]]

Three observations from this round shaped the final system. First, grammar-constrained structured outputs made JSON validity a non-issue: every role of every model produced valid output on the first attempt (for example {{model_selection_r1.results.gemma3:4b.roles.context_gate.valid_first_attempt|ci}} for the Context Gate of `gemma3:4b`), so the choice between models depends on routing quality and speed rather than on parse failures. Second, routing accuracy was modest for all three models: strict accuracy was {{model_selection_r1.results.gemma3:4b.routing.accuracy_strict|ci}} for `gemma3:4b`, {{model_selection_r1.results.qwen3.5:4b.routing.accuracy_strict|ci}} for `qwen3.5:4b` and {{model_selection_r1.results.qwen3:8b.routing.accuracy_strict|ci}} for `qwen3:8b`, with wide intervals on 59 turns. The per-class figures showed why. The Context Gate asked for clarification far too often; `gemma3:4b`, for instance, chose SOFT-ASK {{model_selection_r1.results.gemma3:4b.routing.per_class.SOFT-ASK.predicted|int}} times for {{model_selection_r1.results.gemma3:4b.routing.per_class.SOFT-ASK.support|int}} turns whose gold action was SOFT-ASK, including many unanswerable questions that should have passed to Gate 2 and been declined there. `qwen3:8b` instead over-used GENERALIZE. All emergency turns were escalated by every model because the deterministic fast-path, not the model, handles them. Third, the 8-billion-parameter model was about twice as slow per turn as the 4-billion-parameter models (median {{model_selection_r1.results.qwen3:8b.latency_turn_p50_ms|s}} s against {{model_selection_r1.results.gemma3:4b.latency_turn_p50_ms|s}} s for `gemma3:4b`) without being more accurate on the strict measure.

These findings led to a rewrite of the routing rules of both gates (Section 3.4): Gate 1 now asks only when all three conditions for a missing fact hold and always lets general, out-of-domain, fabricated-entity and false-premise questions through, and Gate 2's "absent from the evidence" rule was restricted to specific named products. The few-shot examples were decontaminated against the benchmark at the same time. Because these changes were driven by the development split only, the test split remains untouched.

## PII Redaction Evaluation

The redactor was evaluated at span level with `scripts/pii_eval.py` on two synthetic sets (`reports/privacy_redaction_metrics.json`, `reports/privacy_redaction_metrics.md`). The development set (240 messages, 183 gold spans, 90 identifier-free but clinically dense negatives) was written together with the detector and used to develop it, so its numbers are in-sample. The blind held-out set (237 messages, 203 gold spans, 89 negatives) was written afterwards by a different author who had no access to the detector, its evaluation script or its earlier metrics, and covers Indian, US and UK contexts in formal, casual, Hinglish and SMS-style language. The detector was frozen, its SHA-256 hash recorded, and the blind set was evaluated once; the evaluation script reloads the frozen detector from version control and checks its hash, so the blind numbers can be reproduced exactly. A span counts as correct under *strict* matching when its character offsets and category both match, and under *overlap* matching when it overlaps a gold span of the same category.

Structured identifiers transfer well: Aadhaar, PAN, Social Security numbers, e-mail addresses and IP addresses were all found, and phone numbers, PIN codes and dates of birth almost all. Names are the weak point: only {{pii.datasets.blind_v2.results.all.per_category_strict.NAME.tp|int}} of {{pii.datasets.blind_v2.results.all.per_category_strict.NAME.support|int}} blind-set names were found (recall {{pii.datasets.blind_v2.results.all.per_category_strict.NAME.recall|f3}}), although almost every predicted name was correct. The detector finds names only after contextual cues ("my name is", greetings, sign-offs, titles), and the blind author used many cues it did not know ("X here", "X this side", "From: X") as well as names with no cue at all. This is a deliberate trade-off: a cue-free name detector would risk redacting drug brand names that look like proper nouns, such as Telma or Concor. Address spans were the second weakness under strict matching because of boundary errors on Indian, US and UK formats, although overlap matching shows that most addresses were at least partly masked.

Two results matter most for safety. First, no protected clinical value (BP reading, laboratory value, dose, drug name, age or date of a reading) was corrupted in either set ({{pii.datasets.blind_v2.results.all.protected_values_corrupted|len}} corrupted values on the blind set). Second, only {{pii.datasets.blind_v2.results.all.negatives_altered|len}} of the 89 blind negatives was altered: "Dr. Google" was treated as a person. After the blind run, a code review found an address-boundary bug, and that bug class and the "Dr. Google" false positive were fixed with general rules; re-scoring the blind set with the fixed detector gives a strict F1 of {{pii.datasets.blind_v2.post_hoc.results.all.overall_strict.f1|f3}}, but this post-hoc figure is optimistic and is not an independent estimate. Mean detection time was {{pii.datasets.blind_v2.results.all.mean_latency_ms|f3}} ms per message on the blind set, negligible compared with a language-model call. The evaluation shows that rule-based redaction is effective for structured identifiers and safe for clinical content, but that reliable name removal would need a named-entity model or a gazetteer, which is listed as future work.

## Emergency Classifier Evaluation

The emergency classifier was developed against two labelled case files: an English file of 288 synthetic messages (156 that must escalate and 132 that must not) and a Hinglish and Indian-English file of 141 messages (90 and 51). The negative cases are deliberately hard: negated symptoms ("no chest pain"), educational questions, historical mentions, breathlessness during heavy exercise, BP targets and conditional thresholds, dates, doses, laboratory values, unrelated number pairs and ordinary words one letter away from a symptom. The unit test `test_precision_recall_summary` in `medbridge/tests/unit/test_emergency_nl_patterns.py` requires zero false positives and zero false negatives on both files, and the classifier passes. These figures must be read with care. Both files were written alongside the rules, so they show that the intended phrasings are covered and that the context filters behave as designed; they are not an independent estimate of real-world accuracy. The independent estimate comes from the emergency items of the HalluBench test split, which were written separately and are reported with the hallucination study. The classifier is also deliberately biased towards recall. Questions about side effects that name a red flag ("can beta-blockers cause shortness of breath?") are escalated, and because the fast-path cannot be overruled by Gate 2, these are its main known source of false positives. Some phrasings are not supported: BP values written in words ("two hundred over one twenty"), readings in cmHg, and the abbreviation "SOB" on its own. A bare number pair with no BP wording must exceed both thresholds, so "200/100 is that bad?" is not escalated by itself. The classifier is deterministic, has no model or network dependency, and the test suite enforces its 10 ms time budget.

## Performance Optimisation

The Review-3 presentation reported latencies of 25.2 s for an ABSTAIN turn and 35.8 s for a GENERALIZE turn. A baseline was re-measured on the received code before any change, with `gemma3:4b`, one cold pass and three warm passes over five scenarios (`reports/performance/before_gemma3-4b.json`). In that baseline, the first out-of-domain ABSTAIN turn took {{perf.before_gemma3-4b.cold.1.latency_s|f1}} s cold and a median of {{perf.before_gemma3-4b.warm_summary.S2-t1:ABSTAIN.p50|f1}} s once warm, which shows that model loading dominated the cold turn. A single-turn ANSWER with a full context took {{perf.before_gemma3-4b.cold.5.latency_s|f1}} s cold and a median of {{perf.before_gemma3-4b.warm_summary.S5-t1:ANSWER.p50|f1}} s warm, and the emergency fast-path answered in a median of {{perf.before_gemma3-4b.warm_summary.S1-t1:ESCALATE.p50|f3}} s.

The following optimisations were implemented, each without changing the routing semantics.

- **Warm-up at start-up.** Embedders, reranker and language models are loaded in the background when the server starts, and the models are kept resident with a keep-alive period, removing the cold-start penalty from the first patient turn.
- **Native structured outputs.** Grammar-constrained JSON removes repair loops and retries caused by malformed output; first-attempt validity was complete in the first model-selection round.
- **Thinking disabled and bounded outputs.** The reasoning traces of hybrid models are switched off and every call has a role-specific token limit.
- **Persistent HTTP client.** One client with connection reuse and explicit timeouts serves all model calls.
- **Concurrent encoding and caching.** Dense and sparse query encoders run in parallel threads; query embeddings and fused retrieval results are cached.
- **Speculative retrieval.** Retrieval overlaps with Gate 1 and is discarded on SOFT-ASK; the saved time is recorded in every trace.
- **Reranker on the GPU.** The cross-encoder runs on CUDA or Apple MPS when available, in a worker thread.
- **Single database flush.** One flush per turn replaces five or more.
- **Deterministic shortcuts.** Small talk is answered by a template without any model call, and erased sessions are rejected before any pipeline work.
- **Smaller evidence units.** Chunks of at most 400 tokens fit the embedder and reranker windows, so no text is silently truncated and prompts are shorter.

## Code Review and Quality Assurance

Before the final experiments, the integrated system was put through an adversarial code review. Reviewers examined seven areas (architecture invariants, validity of the ablation study, statistics and judges, privacy and security, persistence and database, prompts and language-model handling, and the web interface) and proposed defects; each proposed defect was then checked independently three times, and only defects confirmed by all three checks were accepted. ## Limitations

The results above should be read in the light of the following limitations, grouped by theme.

### Knowledge Base

- **Missing guidelines.** Several major documents could not be downloaded by script because the publishers serve a browser check that the project did not attempt to bypass: the 2023 ESH hypertension guideline, the 2022 AHA/ACC/HFSA and 2021 ESC heart-failure guidelines (with its 2023 update), the full 2023 ACC/AHA chronic coronary disease guideline (only a review of it is included), the 2024 ESC guidelines on chronic coronary syndromes and atrial fibrillation, the 2019 ESC/EAS dyslipidaemia guideline and the ISSHP pregnancy guidance [@mancia2023esh; @heidenreich2022hf; @virani2023ccd]. NICE and PMC documents were used as substitutes, but heart failure and coronary disease remain thinly covered, and the cholesterol guideline is represented only by its executive summary. Questions in these areas are more likely to be generalised or declined.
- **Licensing questions.** The ESC 2024 guideline, one of the three original documents, reserves text-and-data-mining rights, and the ISH 2020 guideline was obtained from a co-author's institutional repository. Both are flagged in the manifest for a decision by the team; the ADA Standards of Care section was excluded for its licence.
- **Parsing artefacts.** Section headings are detected heuristically, so some figure text appears as section titles and some appendix noise survives. HTML sources have no physical pages, so their citations refer to section numbers.

### Benchmark and Evaluation

- **Synthetic, single-author benchmark.** HalluBench was drafted by one author with the help of an AI assistant, without clinician review or inter-annotator agreement on the gold labels. Casual English dominates the styles, and there is only one Hinglish item. Some items are borderline between neighbouring categories, and the labels depend on the corpus version.
- **Judge limitations.** The LLM judge is itself a language model; in a development smoke test with a smaller judge model, a claim's label changed when another claim was removed from the same batch, so labels can depend on batch context. The NLI judge's thresholds are calibrated against the LLM judge, so the two judges are not fully independent. The 50-item human annotation sheet that would validate both judges must be completed by the team. Claim decomposition is a judgement in itself, and the boilerplate filter, although narrowed, decides which sentences count as claims.
- **Memoisation.** Identical requests return identical cached outputs across conditions. This is intended, because it isolates the effect of pipeline structure, but it means raw latencies of later conditions are not meaningful; latency is reported as cache-imputed or from uncached runs.
- **In-sample component metrics.** The emergency case files and the PII development set were written alongside the rules they test. Their perfect or near-perfect scores show coverage of intended phrasings, not real-world accuracy; the blind PII set and the HalluBench emergency items provide the independent estimates.

### Privacy

- **Name recall.** The rule-based redactor misses names without a known cue (blind-set name recall {{pii.datasets.blind_v2.results.all.per_category_strict.NAME.recall|f3}}), and some address boundaries, UK formats and scheme-less URLs are not handled. Identifiers that survive redaction are still encrypted at rest and never leave the machine, but they do reach the local model.
- **Key management.** Master-key rotation is not implemented, and losing the master key makes every stored session unreadable. Session tokens are stateless, so erasure does not revoke a token; the session simply answers HTTP 410 afterwards. Rows written before encryption was introduced remain in plaintext in the append-only tables and are only hidden.
- **Single-process controls.** The rate limiter is in memory and per process, and client IP addresses behind a reverse proxy are deliberately not trusted.

### System and Deployment

- **Single node.** The application is designed for one Uvicorn worker on one machine. Per-session turn locks work within a process; across several workers the database row lock still keeps the snapshot consistent, but the soft-ask counter would become last-write-wins. Horizontal scaling is out of scope.
- **Simulated streaming.** The generator returns validated JSON, so the text is streamed only after the whole turn has finished. Stage progress is real, but the first word appears at the end of the turn, and the interface should not be read as token-level streaming.
- **Latency.** Each language-model turn takes several seconds to tens of seconds on the development machine because of the sequential model calls, even after optimisation.
- **Windows not verified by the authors of this report.** The software is cross-platform and provides PowerShell scripts, but its behaviour and latency on the Windows 11 laptop with the RTX 4050 GPU, the CUDA code path of the reranker and verifier, and rendering in Edge, Firefox and Safari and with a screen reader were not tested in this work.
- **Small local models.** The 4 to 8 billion parameter models that fit the target GPU route less accurately than large hosted models, and their generated answers can still contain advice that is not in the evidence; citation validation only checks that markers point to real passages, not that the passage supports the sentence. The hallucination study measures this residual risk, and Gate 3 (V2) is the mechanism designed to reduce it once calibrated.
- **Drug lexicon.** The brand-to-generic mappings, including the Indian brands, come from the authors' knowledge and were not checked against an external drug database, and fuzzy matching does not catch a single-character typo in short brand names.

### Scope and Regulation

MedBridge is a research prototype. It has not been clinically validated, it is not a medical device, and it must not be used for diagnosis or treatment decisions. All development and evaluation data are synthetic; behaviour on real patient conversations has not been studied.
