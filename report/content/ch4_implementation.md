# Implementation and Results

This chapter covers the implementation, interface, testing, component evaluations, code review, hallucination study, live robustness benchmarks and limitations. Every number is read from a results file; missing values are marked as pending.

## Implementation Details

**Application and API.** At start-up (`medbridge/main.py`) a background task loads the encoders and reranker, probes Qdrant and asks Ollama to keep the models resident, so that the first message should not pay the model-loading cost of the received prototype; in the post-study probes this held for `gemma3:4b` but not for `qwen3.5:4b` (Section 4.8). A second task runs the retention job. One `Settings` class (`medbridge/config.py`) defaults to fully local operation: local-only mode, gate temperature 0.0, generator temperature 0.3, seed 42, loop-breaker at 2, and speculative retrieval, redaction, encryption and authentication on. V1 is off. V2 has been on by default since the hallucination study (Section 4.10). Each response carries the text, action, citations, counter, redaction count and `Explanation`. The streaming endpoint runs the same orchestrator call in a background task and emits `stage` events, then `meta`, `token` events that replay the validated text and `done` (or `error` and a safe `done`); a disconnect does not stop the turn, and an erased session gets HTTP 410 before any pipeline work.

**Orchestrator and language-model layer.** The original `_execute_pipeline`, a method of about 390 lines in a 539-line module, became one short method per stage with injected collaborators, so unit tests replace any component with a fake and check every route and fallback without a model. All model calls go through `ResilientLLMWrapper`, which sends the JSON schema of the expected Pydantic model as Ollama's `format` parameter; decoding is therefore grammar-constrained and small local models return valid JSON. Calls set temperature, seed, context size and a token limit, disable "thinking" on hybrid models and share one HTTP client; failures are retried with backoff, a truncated reply is retried once with a doubled budget and never repaired or cached, and when every attempt fails the orchestrator applies the fallback. Prompts have a system part (role, ordered rules, examples on topics absent from the benchmark) and a user part containing only data blocks. The extractor sees the last four turns to resolve references such as "that dose". The generator has the production `grounded` mode and the evaluation-only `direct`, `vanilla` and `prompt_safety` modes of C0 to C2.

**Retrieval, ingestion and persistence.** The retriever sends one Qdrant query with dense and sparse prefetch branches of 20 candidates and RRF with *k* = 60, caches non-empty results and raises `RetrievalError` on infrastructure failure, so an outage is never mistaken for "nothing relevant found"; the reranker selects CUDA, MPS or CPU. Ingestion verifies each file against its manifest checksum and stores each chunk with document, organisation, year, section, page range, URL, topics and checksum. The turn store encrypts every text field and flushes once; four Alembic migrations define the schema.

**Features and evaluation package.** A BP log classifies readings into the ACC/AHA categories with a deterministic function, and manual entries become BP_READING events through the same projection, so the chart and the gates see the same data. A clinician summary exports the snapshot, BP log and each answer with its action and citations under a disclaimer, and an administrator dashboard shows actions, gate decisions, fallbacks, latency, feedback and redacted audit entries. The evaluation package implements Section 3.6 with resumable runs and a circuit breaker after consecutive degraded items, and the AQ, RABBITS, adversarial, smoke, load and latency harnesses run live; their mock modes remain only as labelled self-tests.

## User Interface

The Streamlit interface was replaced by a single-page application served by FastAPI (`medbridge/web/`), written in plain HTML, CSS and JavaScript with no build step or third-party scripts, so it runs offline under the strict Content Security Policy; Markdown is rendered by an escape-first renderer. It offers a searchable conversation sidebar, a 2,000-character composer, light and dark themes, a mobile layout and keyboard and screen-reader support. A live stepper shows the streamed stages, each answer carries a colour-coded action badge, and citation markers open a source drawer with guideline, organisation, year, section, page and excerpt (Figure 4.1). The "Why this answer?" panel (Figure 4.2) shows the decision path, each gate's decision, source and rationale, the reranked passages and per-stage latency without recomputing anything, and an ESCALATE response is an emergency card with the configured numbers (112 and 108 for India; Figure 4.3).

## Model Selection

The application model performs extraction, both gate decisions and generation, and should fit a 6 GB GPU at 4-bit quantisation. `gemma3:4b` [@gemmateam2025gemma3] (the Review-3 model), `qwen3:8b` [@yang2025qwen3] and the later `qwen3.5:4b` of the same family were compared by running C5 on the development split only, recording routing accuracy with Wilson intervals, per-class recall, macro-F1, first-attempt JSON validity, latency and throughput (routing measures the gates, not hallucination). `qwen3:8b` (5.2 GB of weights) is the larger model and would be expected to spill to the CPU on the 6 GB GPU once its KV cache is added. A first round on {{model_selection_r1.generated_at|date}} used the prompts from before the code review (Table 4.5).

[[table:model_selection_round1|Model selection, round 1 (C5, development split)]]

In round 1 grammar-constrained outputs made every role of every model valid on the first attempt (for example {{model_selection_r1.results.gemma3:4b.roles.context_gate.valid_first_attempt|ci}} for the Context Gate of `gemma3:4b`). Strict routing accuracy was modest: {{model_selection_r1.results.gemma3:4b.routing.accuracy_strict|ci}} for `gemma3:4b`, {{model_selection_r1.results.qwen3.5:4b.routing.accuracy_strict|ci}} for `qwen3.5:4b` and {{model_selection_r1.results.qwen3:8b.routing.accuracy_strict|ci}} for `qwen3:8b` on 59 turns. The Context Gate over-asked (`gemma3:4b` chose SOFT-ASK {{model_selection_r1.results.gemma3:4b.routing.per_class.SOFT-ASK.predicted|int}} times for {{model_selection_r1.results.gemma3:4b.routing.per_class.SOFT-ASK.support|int}} gold SOFT-ASK turns), `qwen3:8b` over-used GENERALIZE, and `qwen3:8b` was about twice as slow (median {{model_selection_r1.results.qwen3:8b.latency_turn_p50_ms|s}} s against {{model_selection_r1.results.gemma3:4b.latency_turn_p50_ms|s}} s) without being significantly more accurate (its strict accuracy was below that of `qwen3.5:4b`, and all intervals overlap). The routing rules were therefore rewritten (Section 3.3): Gate 1 asks only when the question concerns the patient's own cardiovascular care, a specific personal fact would change the safe answer, and that fact is missing, and Gate 2's "absent from the evidence" rule was restricted to named products. These rule changes were based on the development split only, and the few-shot examples were decontaminated against every HalluBench turn at the same time. The final round repeats the protocol with the revised prompts (Table 4.6, Figure 4.4).

The rule gives priority to lenient accuracy and macro-F1, with attention to SOFT-ASK and ABSTAIN recall, subject to the 6 GB limit and acceptable latency, preferring the faster model where intervals overlap. `qwen3.5:4b` was chosen for all four roles. ## Performance Optimisation

Review 3 reported 25.2 s for an ABSTAIN and 35.8 s for a GENERALIZE turn. A latency probe (`scripts/latency_probe.py`) replays five scenarios (six turns) through the HTTP API, once cold with the models unloaded and then three times warm, and was run on the received prototype and on the post-study code with Gate 3 enabled (7a3bc67 working tree, before `16e594b`, which changes only turns in which Gate 3 rejects every claim), both with `gemma3:4b`, so that the model is the same (Table 4.10, Figure 4.5). The optimisations preserve the routing semantics: warm-up with keep-alive, structured outputs without repair loops, "thinking" disabled and bounded outputs, a persistent HTTP client, concurrent encoding with caches, speculative retrieval, GPU reranking, one database flush per turn, small-talk templates and chunks that fit the encoder windows.

## Code Review and Quality Assurance

Before the final experiments an adversarial review of seven areas (invariants, ablation validity, statistics and judges, privacy, persistence, prompts, web interface) checked every proposed defect three times independently. It confirmed 37 findings (5 high, 17 medium, 15 low severity), rejected 3, and all 37 were fixed in commit `10aef5e` with regression tests (`docs/notes/code_review_findings.md`). The high-severity findings would have biased the study or the patient state: degraded turns counted as valid outcomes; a vector-store outage logged as an empty retrieval, favouring gated conditions; a filter meant for non-clinical claims that also removed clinical ones; concurrent writers dropping snapshot events; and target questions recorded as BP readings. Medium fixes included a vanilla baseline that had used the production safety prompt and gate examples containing a benchmark item's fabricated drug. All prompts changed, so cached outputs were invalidated and the study and final model-selection round were run afterwards.

## Limitations and Threats to Validity

- **Knowledge base.** Publishers' browser checks, which were not bypassed, kept several guidelines out, among them the 2023 ESH, the recent heart-failure and atrial fibrillation guidelines, the full 2023 chronic coronary disease guideline (only a review is included) and ISSHP pregnancy guidance [@mancia2023esh; @heidenreich2022hf; @virani2023ccd]. Heart failure and coronary disease are thinly covered. The two licence questions of Section 3.7 remain open: ESC 2024 reserves text-and-data-mining rights, and the indexing terms of the ISH 2020 repository copy are unconfirmed.
- **Benchmark and judges.** HalluBench was drafted by one author with an AI assistant, without clinician review or inter-annotator agreement, mostly in casual English. Only the LLM judge, whose labels can depend on the other claims in a batch, scored the gated conditions; the NLI judge was calibrated against it, and no human labels were collected; an AI annotator, stricter than the LLM judge, agreed with it moderately (Section 4.11). Study latencies are cache-imputed, not user-facing.
- **In-sample component metrics.** The emergency files and the PII development set were written with the rules; the blind PII set and HalluBench give independent estimates.
- **Privacy.** Names without a known cue are missed (blind recall {{pii.datasets.blind_v2.results.all.per_category_strict.NAME.recall|f3}}) and reach the local model, though encrypted at rest. Key rotation and token revocation are missing, pre-encryption rows stay in plaintext (hidden), and rate limiting is per process.
- **System.** One Uvicorn worker is assumed (across workers the soft-ask counter would become last-write-wins), and concurrent users queue behind one model server (Section 4.8). Streaming is simulated: stages are live, but text is replayed after the turn. The 4-billion-parameter model routed only {{model_selection.results.qwen3.5:4b.routing.accuracy_strict|ci}} of development turns exactly right (Table 4.6) and can still state advice absent from the evidence that Gate 3 misses, such as an accepted false premise. The Windows target laptop, CUDA paths, other browsers and screen readers were not tested by the authors, nor was the brand lexicon checked against a drug database.
- **Post-study changes and provenance.** The live AQ run and the C0–C5 study runs evaluated the code before four later commits. The V2, V12, most C1G and the retry test runs used the first, `3f58b59`, which only serialises PyTorch loading and inference behind one process-wide lock (Gate 3 and the reranker, running concurrently on Apple MPS, had crashed the study process); no study run includes the other three. `02d9774` is the brand-name fix prompted by live RABBITS. `7a3bc67` enables Gate 3 by default with the development-calibrated θ = 0.2 and τ = 1.0, applying by analogy the brief's rule for a winning variant. `16e594b`, found by reading the code after the study, withdraws a draft in which Gate 3 rejects every claim instead of delivering it unchanged (an ANSWER is regenerated as GENERALIZE and abstained if that fails too; a GENERALIZE draft is abstained): in the V2 test runs this happened in {{study_gate3.V2.all_unsupported|int}} of the {{study_gate3.V2.turns_checked|int}} turns in which Gate 3 checked claims, {{study_gate3.V2.all_unsupported_hallucinated|int}} of them rated hallucinated, and the fix was not re-measured. RABBITS was re-run after the brand-name fix with Gate 3 off (fb38cf6, before 7a3bc67) and the adversarial suite at 7a3bc67 with Gate 3 on; both re-runs, the latency probes and the load test predate `16e594b`, and only the smoke test and the screenshots used the final code. HalluBench and AQ were not re-run, so their numbers describe the studied code.
- **Usefulness cost of Gate 3.** Gate 3 deletes unsupported sentences instead of rewriting them. In the final screenshot runs, "My blood pressure was 145/92 this morning. Is that high?" received a one-sentence GENERALIZE reply: five of six claims fell below θ = 0.2, and the remaining sentence had no citation, so the citation rule downgraded the ANSWER. The study runs already show this mechanism: in {{study_gate3.V2.citation_downgrades|int}} of the {{study_gate3.V2.turns_checked|int}} V2 test turns Gate 3 checked, it removed every validly cited sentence and the citation rule turned C5's ANSWER into GENERALIZE. This is the coverage side of the study's finding that V2 reduces hallucination largely by shortening answers ({{study.per_condition.V2.llm.claims_per_response|f1}} against {{study.per_condition.C5.llm.claims_per_response|f1}} claims per response).
- **Scope.** A research prototype tested on synthetic data only, not a medical device.
