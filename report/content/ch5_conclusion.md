# Conclusion and Future Work

## Summary of Work Completed

The project set out to build a conversational assistant for hypertension and cardiovascular care that decides, before writing any clinical text, whether it is entitled to answer. MedBridge implements this as a Dual Answerability Gate inside the approved eight-step pipeline. The architecture and its invariants were kept while the orchestrator was rewritten as traced stages with a single database flush, speculative retrieval, citation validation and correct multi-turn follow-ups. The emergency fast-path became a deterministic rules engine for colloquial, negated, misspelt and Hinglish phrasing within 10 ms. The corpus grew from 3 to {{corpus.totals.documents|int}} curated, checksummed documents. All inference runs locally with grammar-constrained outputs, and a calibrated Evidence Gate (V1) and a grounding verifier (V2) were added. Redaction before any model call, signed session tokens, per-session encryption and crypto-shredding erasure removed the Review-1 privacy and authentication limitations, and a chat interface with streamed progress, citations and a "Why this answer?" panel replaced Streamlit. Finally, MedBridge-HalluBench and an evaluation package with ten conditions, two judges, development-only calibration, degraded-turn accounting and paired statistics were built, the AQ, RABBITS, adversarial, smoke and load harnesses were run live, and an adversarial code review fixed 37 defects before the final experiments.

## Conclusion

This project showed that the decision of whether to answer can be made an explicit, auditable part of a retrieval-augmented medical assistant. MedBridge separates the two reasons for holding back, insufficient patient context and insufficient evidence, into two gates, places a deterministic emergency check in front of both, and routes every message to one of five actions whose provenance is logged immutably and shown to the user, on a single laptop with no patient text sent to any external service.

The component evaluations support several design choices and expose clear limits. Grammar-constrained decoding made the output of small local models reliably parseable. Hybrid retrieval ranked best (its intervals overlap those of dense retrieval), and the reranker, which did not improve ranking, is kept mainly as an evidence signal. Rule-based redaction proved precise and safe for clinical values but missed many personal names in a blind test. Live testing after the study found and fixed a brand-name fragility.

The evaluation answers the four research questions. For RQ1, the dual gate significantly reduced both hallucination and unsafe answers compared with vanilla RAG and prompt-only safety (risk differences of {{study.tests.mcnemar.1.risk_difference.estimate|pp}} and {{study.tests.mcnemar.6.risk_difference.estimate|pp}} against C1). It achieved this mainly by abstaining selectively, at a cost in coverage. For RQ2, the Evidence Gate accounts for most of the effect, while the Context Gate adds little beyond turning refusals into clarification questions. For RQ3, the grounding verifier (V2) further reduced hallucination (its reduction of unsafe answers, {{study.per_condition.V2.llm.unsafe_answer|pct}} against {{study.per_condition.C5.llm.unsafe_answer|pct}}, was not significant) and was enabled by default; the calibrated Evidence Gate (V1) brought no benefit. For RQ4, the complete system runs on one consumer laptop with locally hosted models (measured on an Apple M5; the RTX 4050 target was not tested). With `qwen3.5:4b`, warm answers took {{perf.after_qwen3.5-4b.warm_summary.S5-t1:ANSWER.p50|f1}} to {{perf.after_qwen3.5-4b.warm_summary.S4-t2:ANSWER.p50|f1}} s, an abstention {{perf.after_qwen3.5-4b.warm_summary.S2-t1:ABSTAIN.p50|f1}} s and an emergency a few milliseconds. One model server serves one user at a time, so the system is feasible for a single user but slow. These conclusions rest on one LLM judge for the gated conditions, a synthetic benchmark and one run per condition. They show that the architecture reduces unsupported output on this benchmark, not that it is clinically safe.

The project also leaves a reproducible method for testing such claims: benchmark categories that mirror the routing decisions, paired conditions that differ only in pipeline structure, a cross-family LLM judge with an NLI agreement check and a human sheet, development-only calibration, accounting of degraded turns, and statistics with intervals and multiplicity correction.

## Limitations and Future Enhancements

The limitations are discussed at the end of Chapter 4. The following enhancements address them.

1. **Complete the knowledge base.** Obtain the missing heart-failure, ESH, chronic coronary disease and ESC atrial fibrillation guidelines through institutional access, resolve the licence questions and name each source when guidelines disagree.
2. **Clinician-validated benchmark and stronger evaluation.** Have clinicians review the HalluBench labels with inter-annotator agreement, add multi-turn, Hinglish and regional-language items, complete the human annotation sheet, use a panel of judges or a larger judge with one claim per call, and repeat the study on both target machines.
3. **Better-calibrated abstention.** Add a conformal or selective-prediction threshold on gate confidence so that abstention can be set to a target risk level [@angelopoulos2023conformal], and evaluate the MedCPT cross-encoder as the V1 evidence signal.
4. **Grounding verification and real streaming.** V2 should rewrite unsupported sentences instead of deleting them, so that answers stay complete and coherent, use a stronger clinical NLI model, check numbers, drug names and false premises explicitly, and be recalibrated on more than 59 turns and confirmed by a second judge and human labels; the effect of withdrawing fully unsupported drafts (`16e594b`) must be measured. Generator output should be streamed with sentence-level validation.
5. **Stronger privacy.** Add a local named-entity model or gazetteer for names without a cue, master-key rotation, token revocation and storage of the master key in the operating system's key store.
6. **Multilingual use, deployment and studies.** Extend understanding to Hindi, Tamil and Hinglish; verify installation, performance and accessibility on the Windows target laptop; support several workers and a shared model server; and run an ethics-approved usability study and a prospective clinical evaluation before any real-world use.
