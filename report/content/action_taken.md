#* Action Taken on Previous Review Comments

The table below records the observations made at the earlier reviews and in the audit of the Review-3 deliverables, the action taken on each, and where the evidence can be found in this report and in the repository. Section numbers refer to this report; file paths are relative to the repository root. Rows marked [TO BE FILLED] are reserved for the comments recorded by the panel at Review 3 and at the draft report review, which the team adds verbatim together with the action taken.

Table: Action taken on previous review comments
| No. | Comment or observation | Action taken | Evidence |
|---|---|---|---|
| 1 | The MedBridge-AQ benchmark result shown earlier was produced in mock mode (no language model was called), so the claimed absence of hallucination had no empirical support. | Built a live, statistically analysed hallucination study: the synthetic MedBridge-HalluBench benchmark (247 items, development and test splits), an evaluation package that runs every item through the real pipeline, two independent judges plus a human annotation sheet, and paired tests with confidence intervals. The AQ benchmark was rebuilt with 275 vignettes and now runs live; mock-mode reports are labelled as routing simulators and are never used as results. | Section 3.7; hallucination study results in Chapter 4; `evaluation/`; `evaluation/datasets/hallubench_v1.json`; `tests/benchmark/` |
| 2 | The final specification promised an ablation study and three baselines, which were not implemented. | Implemented six study conditions as internal presets of the production orchestrator: direct LLM (C0), vanilla RAG (C1), RAG with prompt-only safety (C2), Context Gate only (C3), Evidence Gate only (C4) and the full dual gate (C5), plus two extensions, a calibrated Evidence Gate (V1) and a grounding verifier (V2). The vanilla baseline uses a plain RAG prompt so that it differs from the production prompt. | Section 3.4 (V1, V2); Section 3.7 (conditions); `medbridge/core/pipeline_types.py`; study results in Chapter 4 |
| 3 | Review-1 limitation: the PII anonymisation layer was deferred. | Added a privacy layer: deterministic redaction of personal identifiers before any model call, log line or database write; per-session envelope encryption at rest; erasure by crypto-shredding that keeps the audit log append-only; log scrubbing; automatic retention. Redaction was evaluated on a development set and once on a blind held-out set. | Section 3.6; Section 4.6; `medbridge/privacy/`; `reports/privacy_redaction_metrics.md`; `tests/privacy/` |
| 4 | Review-1 limitation: no authentication (session identifier only). | Every session route now requires a signed, expiring HMAC-SHA256 bearer token bound to the session; the dashboard has a separate administrator login; rate limits, a request-size limit, a strict Content Security Policy and other security headers were added. | Section 3.6; `medbridge/privacy/tokens.py`, `deps.py`, `middleware.py`; `tests/privacy/test_tokens_and_deps.py` |
| 5 | Review-1 limitation: dependence on external LLM APIs. | All inference runs locally through Ollama; a local-only mode, enabled by default, refuses remote providers and non-loopback endpoints, so no patient text leaves the machine. The application model was chosen by a model-selection experiment among models that fit a 6 GB GPU. | Section 3.6; Section 4.5; `medbridge/ai/llm_wrapper.py`; `evaluation/results/model_selection/` |
| 6 | High latencies in the Review-3 demonstration (25.2 s for ABSTAIN and 35.8 s for GENERALIZE). | Re-measured the baseline, then added model warm-up at start-up with keep-alive, grammar-constrained structured outputs, concurrent dense and sparse encoding, query and result caches, speculative retrieval that preserves the gate semantics, GPU reranking, deterministic small-talk handling and a single database flush per turn. | Section 3.4 (speculative retrieval); Section 4.8; `reports/performance/` |
| 7 | The pipeline was a fully sequential 540-line method that loaded models lazily, flushed the database five or more times per turn and deep-copied retrieved chunks. | Refactored the orchestrator into traced stage methods with the same order and routing semantics, a single persistence step, no deep copies, per-session turn serialisation, and a per-turn trace stored in the audit log. | Section 3.2; Section 3.4; Section 4.1; `medbridge/core/orchestrator.py`; `medbridge/state/turn_store.py` |
| 8 | The Streamlit interface relied on styling workarounds and did not provide a modern chat experience. | Built a single-page chat application served by FastAPI with streamed progress, action badges, a citation drawer, a "Why this answer?" panel, a patient-context panel with a BP chart, feedback, export, a dashboard, dark mode and accessibility support. Streamlit is kept as a legacy client. | Section 4.2; Appendix B; `medbridge/web/` |
| 9 | The knowledge base contained only 3 PDF documents. | Expanded the corpus to {{corpus.totals.documents|int}} curated guidelines, statements and patient-information pages with a checksummed manifest, rebuilt ingestion with tokenizer-measured, table-aware chunking, and evaluated retrieval on a labelled query set. | Section 3.8; Section 4.4; Section 4.9; `data/corpus_manifest.json`; `reports/corpus_stats.md` |
| 10 | The README contained Windows-only absolute links and outdated descriptions of the code structure. | Rewrote the README with repository-relative paths and an accurate structure, and added a detailed installation and running guide with separate Windows 11 and macOS instructions. | `README.md`; `HOW_TO_RUN.md` |
| 11 | The RABBITS brand-and-generic test and the adversarial tests had only been run against mocked components. | Rebuilt both as live harnesses: RABBITS over 189 cardiovascular brands (65 of them Indian) and an adversarial suite of 19 injection and jailbreak payloads with deterministic scoring, in addition to hermetic security tests. | Section 3.7 (supporting experiments); system benchmark results in Chapter 4; `tests/adversarial/` |
| 12 | Review-1 limitation: single-node deployment without horizontal scaling. | Retained deliberately for a local, privacy-preserving deployment on one laptop; concurrency within the node is handled by per-session locks and database row locks. The limitation and a path to multi-worker deployment are documented. | Section 3.2 (deployment); limitations section of Chapter 4; Section 5.4 |
